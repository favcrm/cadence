# CAD-1362 — smallest hosted app update delivery path

**Spike result (read-only):** the tenant-side byte transport, bundle validation, content digest, install journal, and file-map upgrade transport already exist in Cadence. The missing product path is AgenticOS resolving a curated release artifact and relaying it through the existing board routes under an authority the tenant daemon will accept. The smallest viable delivery is one AgenticOS feature PR plus one Cadence prerequisite PR on the preserved CAD-1140 lane. No new Cadence upload/install transport PR is justified by the inspected code. CAD-1140 has no open PR; its preserved local lane has an unresolved safety hold. The app remains installed only in the tenant's Cadence catalog.

Evidence below is static source/docs/ticket inspection only. No tenant, production, browser, network, build or install/update operation was performed. `VERIFIED` means the checked source or recorded ticket states this; it does not claim a particular deployed tenant runs that version.

## 1. Cadence tenant entry: bundle bytes, digest, authority and refusals

**VERIFIED — install:** `POST /api/app-installations/upload` is the exact hosted entry (CAD-996). `src/ui/write_path.rs:1374-1385` dispatches the route; it is classified `OperatorOnly` in `src/ui/operator.rs`'s `WRITE_ROUTES`. The handler in `src/ui/apps.rs:53-82, 354-407` accepts a strict `{files, expected_digest?}` JSON object, with duplicate and unknown-key rejection, and passes the file-map to the existing `app_workspace_install` RPC. The outer JSON wire cap is 8 MiB; decoded bundle content is capped at `app::MAX_APP_BYTES` (2 MiB), 128 files, with per-file caps (`apps.rs:57-70, 113-167, 374-407`; `src/issue/app.rs:120`). Files must follow the exact flat bundle allowlist (`apps.rs:282-316`). It stages under a server-derived temporary directory outside the PM tracker, revalidates and journals through the existing installer, and cleans staging on return (`apps.rs:319-407`; `workspace.rs:502-572`).

**VERIFIED — digest and write proof:** when supplied, `expected_digest` is checked against the resolved bundle before lock, catalog read or write (`workspace.rs:452-465, 502-520`). The RPC proves the operator connection and rejects unknown parameters (`src/daemon/plans_rpc.rs:490-555`); `src/daemon/caller_rule.rs:589-597` also marks install and update operations as operator-connection rules. This is not a freely supplied actor/role field. CAD-996 records that the created catalog install uses the current installer/journal, not a second registry, and the upload temp source is not a reusable update source. Since CAD-1119, an operator's install/update is consent to that exact digest (`plans_rpc.rs` post-operation consent at lines 648-663); a future UI must show the checked version/digest and require an explicit Install/Apply action. Do not describe this as a background or silent auto-update.

**VERIFIED — update:** Cadence already accepts `{files}` bundle input on its upgrade-check and upgrade HTTP routes (CAD-1006; `apps.rs:191-196, 409-420, 1029-1064`). It relays to `app_workspace_upgrade_check` / `app_workspace_upgrade` with install id, expected current digest, catalog generation, expected new digest and request id. The daemon checks identity, old digest, generation and proposed new digest before staging the journal (`plans_rpc.rs:501-515, 560-578`; `workspace.rs:576-623, 625-730`). Thus a platform need not pass a caller-controlled path or make the tenant fetch a URL.

**VERIFIED — refusals and limits:** malformed/unknown/duplicate fields, unsafe or duplicate paths, file/count/aggregate/wire overflow, incompatible package requirements, a tampered digest, wrong app identity, stale current digest or generation, and changed new bytes are refused by existing gates. The real HTTP peer is at least as strict as the daemon RPC (`operator.rs` route admission; `plans_rpc.rs:497-555`). Host compatibility is enforced by CAD-1236. The peer check is significant: auth to an AgenticOS API route is not itself a Cadence operator proof.

**UNKNOWN / blocking proof question:** can an authenticated AgenticOS workspace owner action be represented at the Cadence HTTP peer as the exact live operator session plus peer proof required by `OperatorOnly`, without elevating an ordinary member or treating AgenticOS's signed relay proof as a substitute for caller authority? The inspected code does not establish this for writes. Cadence's operator contract says a relay is not itself an operator (`src/ui/operator.rs:1-37`); AOS relay proof authenticates/fences the platform-to-container hop, not the end-user's permission. AOS-176 deliberately forwards the user's workspace role verbatim and does not mint `owner` for a member (`agenticos-v2 origin/main:apps/api/src/installed-apps.ts:22-39, 49-68`). The implementation must reuse an already supported owner/operator session exchange, or define and review a narrowly scoped proof accepted by both HTTP and daemon; it must not forge a role, forward caller-selected actor fields, or weaken the daemon guard. Prove this in the real route before claiming hosted delivery works.

## 2. AgenticOS reachability, relay and AOS-176

**VERIFIED — available pieces:** AOS-175 serves the curated `marketplace/apps.json` listing through `GET /v2/marketplace/apps[/:id]`; it explicitly has no install writer, runtime call, or wake (`agenticos-v2 origin/main:apps/api/src/marketplace.ts:11-26, 51-77`). AOS-176 serves only `GET /v2/workspace/app-installations` for the signed-in user's own workspace; it resolves the workspace server-side, preserves the membership role, and uses the observation-only read path (`installed-apps.ts:12-39, 45-69`). It reads Cadence's catalog; it does not read AOS D1 as a second installation registry.

The shared board runtime helper provides an existing relay to `server.mjs` on container port 3011, forwards only to the loopback Cadence board, attaches a worker-signed relay proof, and revalidates tenant/instance/generation lease authority (`agenticos-v2 origin/main:apps/api/src/board/runtime.ts:67-93, 101-160, 225-250`). `wakeBoardRuntime` is the verified-session path; `peekBoardRuntime`/`observeBoardRuntime` do not wake (same file around lines 27-53, 275, 457, 515). The AOS-168 read relay mints a board assertion and uses an observation-only bounded path; it is a read precedent, not the write implementation (`apps/api/src/admin-app-installations.ts`, session/read helpers; AOS-168).

**Recommendation:** add one authenticated AgenticOS workspace action, bound to the server-resolved workspace and an eligible owner/operator, that takes a listing id and install/update CAS values only. It fetches only the manifest-pinned release, verifies it, then uses the existing tenant board relay to invoke the exact upload or upgrade route. Use the verified explicit-session/wake path when the operator submits the action; never wake from listing/read. Respect a stopped tenant as stopped, report it, and do not bypass lifecycle controls. Keep the relay target fixed to the company's own board and revalidate lease/instance before each forward. Do not reuse AOS-168's no-wake read route as the write transport.

**AOS-176 today:** it returns the runtime catalog when available, and explicit unavailable states when not. It neither supplies marketplace update bytes nor invokes install/upgrade. Current customer Apps UI can show an update from listing metadata, but the Install button is disabled as “Coming soon” pending AOS-126 (`agenticos-v2 origin/main:apps/web/src/apps/AppsPage.tsx:37-40, 321-337, 420-437`).

## 3. Published artifact, digest and listing

**VERIFIED — listing today:** AOS's `marketplace/apps.json` entries carry app identity/version, `{repo, commit, path}` and `digest`; for Social Content the current listing is pinned to repo commit `6526798701f7e5913cb31a5b0c40201257dec8b3`, path `workspace-apps/social-content`, and Cadence digest `sha256:c832f590…` (`agenticos-v2 origin/main:marketplace/apps.json`, Social Content entry). `marketplace/README.md` says this `digest` is the digest printed by `cadence app catalog install-check` (CAD-1186). It is a canonical Cadence bundle digest, not the SHA-256 of a transport archive or JSON wrapper. AOS-175 has no artifact URL/store today.

**VERIFIED — release output:** the Social Content `scripts/package-ui-release.mjs` builds a flat `{files}` `upload.json` and a `SHA256SUMS.txt` with per-file hashes; its current script header/validator targets a 0.5.2, 10-file screen release. It does not emit the raw `upload.json` artifact hash as the Cadence bundle digest. The inspected `/tmp/demo-app097` kit verifies a bundle file set and uses the result of `upgrade-check` as the expected new Cadence digest before apply (`app.sh:7, 23-37`, `run-check.log`, `DIGEST`). Those logs are evidence of the kit's flow, not proof that the kit ran or that any production tenant updated. The current general release artifact/publisher and the deployment location are **UNKNOWN**; do not infer an existing AOS artifact bucket from the listing.

**Recommendation:** publish the exact packager output as an immutable app-release asset (initially a release asset attached to the app repository's immutable tagged release; alternatively a content-addressed object store if the platform operator selects one). Add both `artifact.url` and `artifact.sha256` over the raw `upload.json` bytes to the curated listing, while retaining the existing Cadence `digest` as the digest of decoded bundle files. The publisher computes raw artifact SHA-256 from the final file; the Cadence digest comes from `install-check` for the exact package. AOS fetches only the URL curated in the listing, permits only the chosen release origin (including redirect checks), verifies raw artifact SHA-256, strictly parses `{files}`, enforces the same count/content cap, then sends `expected_digest` to Cadence, which recomputes it. No user-provided URL, repo HEAD, mutable branch, archive extraction, signing system or new D1 install table is needed. Whether immutable GitHub release assets are acceptable as the first-party hosting location is an operator decision; the currently inspected sources do not establish an existing artifact store.

## 4. Manage page and single control

**VERIFIED:** Cadence's generic Manage page already supports checked update proposals and pinned Apply. It shows an operator-managed source field (`builtin:<id>`, absolute path or Git URL), sends expected current digest/generation for check, displays version/new digest/diff/compatibility, and applies with the returned digest plus request id (`ui/src/features/explorer/ManageApp.tsx:157-208, 225-247`; CAD-1244). It cannot locate a listing release: a `Source::Path` has no upstream, Git checks re-resolve the install's recorded Git source, and built-ins check only embedded bundle bytes (`workspace.rs:1696-1750`; `app-update-install-audit-20261011.md §2`). Hosted containers have no raw egress (AOS-126 ticket); a user-supplied repo root is not the Social Content release output.

**Recommendation:** the one discover/install/update control belongs in the AgenticOS Apps marketplace, replacing its disabled Install action and using the existing Installed/Explore surface. For an absent app, show the curated release and digest then explicit Install. For an installed app, compare its recorded digest/version with the same listing, show Update available and the checked diff, then explicit Apply. The board Manage page can link to the platform action later; adding a second independent artifact resolver there is unnecessary. Existing listing GET and AOS-176 installed read provide the two sides; AOS-126 provides the missing mutation path. There is no auto-update.

## 5. Failure cases and behavior

- **Stale digest/generation — VERIFIED guard:** return a stale-proposal refusal without applying; do not retry with fresh state silently. Cadence rechecks old digest/generation and expected new digest at upgrade (`workspace.rs:600-606, 686-700`). Reviewer acceptance must prove the real HTTP and daemon refusals.
- **Tampered/replaced artifact — VERIFIED defenses / new AOS check required:** AOS raw artifact hash mismatch fails before relay; Cadence recomputes expected bundle digest and refuses mismatch before install writes (`workspace.rs:452-465, 513-520`). Never treat a matching metadata URL as proof of bytes.
- **Unauthorized caller — VERIFIED guard / AOS proof UNKNOWN:** refuse member/non-owner, forged workspace id, forged actor/role, detached or invalid session, and unproven relay at API and tenant peer. AOS relay proof secures the hop but does not grant tenant operator authority. The exact supported owner-to-Cadence proof must be independently confirmed; this is the critical design decision above.
- **Tenant asleep — VERIFIED options:** read path is no-wake. A user-submitted, authenticated action may use the normal verified session/wake path; show progress/failure and do not retry mutation on an ambiguous response. An operator-stopped tenant is refused, not silently resumed.
- **Relay refused/lease changed — VERIFIED transport rule:** fail closed on relay proof, workspace/instance/generation or lease failure; no alternate `exec`, shell, user URL or raw port. If a mutation outcome is uncertain, reread the actual Cadence catalog before retrying; use the existing request-id replay guard for upgrade.
- **Too large — VERIFIED Cadence caps:** reject over 8 MiB encoded or 2 MiB decoded / 128 files / applicable per-file limits before staging. AOS must enforce bounded fetch and bounded parse too; do not increase the tenant cap for this feature.
- **Host incompatibility — VERIFIED CAD-1236:** Cadence refuses unsupported `needs.requires` before catalog/journal/record writes. Surface the refusal; do not publish an alternate, unreviewed bundle.
- **Bindings carry-over — VERIFIED dependency:** current upgrade keeps prior digest-pinned bindings stale when declarations are unchanged; the hosted kit has to recreate them. CAD-1140 is open and specifically requires unchanged declarations to carry bindings, including context-scoped bindings, with readiness immediately `ready`. Do not call update usable until that Cadence fix is merged and its reviewer-authored check proves board/relay behavior. Changed/widened declarations remain a refusal/rebind case as specified there.

## 6. Minimum delivery plan, review risk and acceptance

### Cadence — one prerequisite PR on the existing CAD-1140 lane (not yet opened; not a new transport implementation)

- **Scope:** deliver CAD-1140's binding carry-forward on the existing journaled upgrade path, preserving its independently authored acceptance. The ticket is in review with a blocked-safety tag; its preserved lane has no PR, and comments state the safety hold remains unresolved. Do not resume that lane until its owning PM/operator resolves the hold. A separate upload/marketplace transport change is not indicated by this audit: install upload with expected digest, bounded files upgrade, strict operator proof, CAS and compatibility gate already exist.
- **Acceptance:** the ticket's reviewer-authored check proves same-declaration install-scoped and Default-context bindings move to the new digest atomically; readiness is `ready` and a run dispatches without operator rebind; changed/widened declarations still require explicit rebind; agent/unauthorized caller refuses through real daemon and board HTTP. Include one successful files-mode hosted upgrade with exact old/new digest and generation pins. Preserve history/recovery invariants.
- **Refusal check owner:** reviewer/ticket author, not implementer; must exercise the real gate and fail if binding carry is absent or an agent update succeeds. Do not edit/weaken the existing independent acceptance authored in the CAD-1140 lane.
- **Risk:** `human (7)` — daemon-enforced binding/readiness gate. Require operator approval and the required independent review. This is a precondition for a usable hosted update, and is already an open feature/ticket, not extra CAD-1362 source scope.

### AgenticOS — one AOS-126 delivery PR

- **Scope:** immutable release metadata for the curated listing, bounded AOS-side fetch/hash validation, one customer-facing install/update action, and a fixed per-workspace relay to the existing Cadence upload/upgrade peer. AOS-176 remains a read-through; no install table or second writer. Route proves actor and workspace from the authenticated session, authorizes only the chosen owner/operator, and uses the supported assertion/session/wake + signed relay/lease path. Explicit confirmation is consent to the displayed exact digest.
- **Acceptance:** first-party Social Content and CRM published `{files}` artifact installs when absent and updates when present, through the real route/relay into Cadence; server-side listing lookup chooses URL and company; raw artifact SHA and Cadence digest both match; successful catalog readback reports the expected version/digest. The same operation uses install upload or check/apply upgrade as appropriate. No raw tenant egress, SSH, shell/exec, auto-update, second writer or silent approval. Show binding-ready state after CAD-1140 lands.
- **Refusal check author:** independent reviewer or ticket author writes the adversarial check; it must fail without the real guard. Through the real AgenticOS API and tenant HTTP/RPC it proves: member/forged actor or workspace is refused; a stale digest/generation is refused; altered artifact bytes/hash are refused; oversized bytes are refused; and none changes tenant catalog/journal. Include stopped/asleep/relay refusal and assert no unintended wake or retry; assert authorized explicit action follows intended wake policy. No self-authored echo fake as proof.
- **Risk:** sensitive trust-boundary identity/auth + artifact supply-chain relay; classify at least `human (1, 3)` (plus any actual trigger for route/infra files), two different independent Standards and Spec/security reviewers, and operator approval. Design note in PR must name role/workspace/lease checks, exact digest/CAS, and refusal cases. No production rollout is implied by merge.

**Sequencing:** resolve CAD-1140's safety hold, deliver its one Cadence PR, and merge it before (or in an explicitly compatible order with) the one AOS-126 PR. Do not add another Cadence PR just to duplicate the byte transport. If source inspection or independent acceptance reveals that the current Cadence HTTP peer cannot accept a correctly authorized AOS owner action, stop and scope the smallest narrowly-authorized Cadence peer change as a follow-up; do not bypass the peer. The authority proof is the remaining UNKNOWN that can change this PR count.

## 7. Open decisions / explicitly deferred

1. **Authority mapping (blocking):** does an AOS workspace owner action produce a supported Cadence operator/public-owner session accepted by both upload and upgrade HTTP peers? If not, which explicitly permitted actor (tenant operator vs platform operator) should own the user gesture, and what narrow signed proof may the daemon trust? Current source alone does not settle this.
2. **Artifact hosting:** approve immutable GitHub release asset as the simplest origin, or nominate an existing operator-owned content-addressed object store. No current marketplace artifact URL/store was found. Require raw artifact hash plus Cadence bundle digest either way.
3. **Tenant waking:** permit wake only as a direct, authenticated Install/Apply action; keep no-wake behavior for listing/read. Stopped tenant remains an explicit refusal.
4. **Bindings:** CAD-1140 is a prerequisite for claiming a post-update-ready app; compatible binding migration is not supplied by AgenticOS.

**Not now:** tenant-side Git fetch or arbitrary egress; polling/auto-update; image-bundled app payload; generic shell/`exec`; new Cadence source resolver; D1 installed-app table or second writer; third-party publishing/signatures; independent custom UI loader; binding reauthorization or data migration beyond CAD-1140; production tenant/SSH validation. These are unnecessary for the bounded first-party published-bundle path, or separate gates/features.
