# CAD-173 PTY timer and sub-minute testing investigation

**Date:** 2026-09-21 (UTC)
**Branch:** `cadence/cad-173-efficiency-audit`
**Basis:** the single PR94 GitHub run documented in the [CAD-173 CI efficiency audit](./cad-173-ci-efficiency-audit.md), plus source inspection of the current tree at `6279117b9378ba823ed4a0a6ef8ce3e6b052c156`.

This is a read-only investigation. It does not change production deadlines, retry behavior, the test workflow, PR93/PR94, or required checks. No full-suite run was started. Times labelled as floors or estimates are derived from source constants and test structure; they are not phase measurements.

## Finding

The current suite does not have a credible all-target sub-minute path. The PR94 test job took 325 seconds, including a 37-second inventory/parity step and a 279.150-second nextest execution step. The run reported 662 passed and 0 skipped tests; the integration target alone contributed 1,051.415 seconds of per-test duration across 290 tests. The slowest single test took 68.272 seconds. These facts are from one GitHub run, so they do not establish a stable CI tail or a cost saving.

A sub-minute *fast feedback* lane is plausible after extracting deterministic in-process state transitions and keeping only a small set of process-boundary smoke tests. That lane would be a different coverage claim. The retained end-to-end lane must continue to exercise real child processes, ownership proofs, render deadlines, shutdown grace, and all targets. The historical CAD-173 nextest measurement is not a current guarantee.

There is no Tokio runtime in this repository. The daemon and PTY adapter use `std::time::Instant`, `std::thread::sleep`, condition variables, filesystem state, `/proc`, `flock`, and subprocess I/O. A paused Tokio clock would have no effect on these paths. A test clock can help only after the in-process decision logic accepts a clock or explicit timestamp; it cannot fast-forward a Python child, a fresh tmux command process, a real filesystem/proc proof, or a child process's `time.sleep`.

## Where the time comes from

### In-process timers

The daemon's stall watcher calls `stall_tick` and then sleeps for the fixed 2s `STALL_TICK` ([`src/daemon.rs`](../../src/daemon.rs#L2810-L2819)). `stall_check` captures a PTY screen on a separate thread, allows at most one capture in flight, and requires a candidate screen to be confirmed by a second sample before it updates activity ([`src/daemon.rs`](../../src/daemon.rs#L2970-L3031)). The silence budget is compared against a real `Instant` ([`src/daemon.rs`](../../src/daemon.rs#L3033-L3050)). The tests can override the sample interval and `stall_secs`, but not the outer ticker or clock.

PTY delivery waits 300ms after a successful paste before pressing Enter, then captures every 150ms until a differential render and an empty input line are observed or the 4s render deadline expires ([`src/adapter/pty/mod.rs`](../../src/adapter/pty/mod.rs#L873-L940)). A `NotRendered` routed message is retried three times; each retry waits on a real condition variable until `now + 5s` unless another wake arrives, and the fourth miss is parked ([`src/daemon.rs`](../../src/daemon.rs#L729-L779)). The 3s shutdown grace is also a real deadline with 25ms polling ([`src/daemon.rs`](../../src/daemon.rs#L2742-L2780)).

The integration helpers add polling around durable state: health, agent state, and messages poll RPC every 50ms ([`tests/integration.rs`](../../tests/integration.rs#L59-L117)); the job-event test polls every 200ms ([`tests/integration.rs`](../../tests/integration.rs#L9768-L9783)); the transient screen helper polls the mock capture counter every 30ms ([`tests/integration.rs`](../../tests/integration.rs#L13077-L13105)). These intervals are small compared with the intentional deadlines, but they should be measured rather than assumed to be free.

### Process and operating-system boundaries

The mock tmux command is launched as a fresh child process for every adapter command. The mock pane is another process group, and the tests exercise real `/proc` ownership and `flock` proofs. The mock Devin and Claude loops use Python `time.sleep(0.05)`; a targeted `MOCK_TMUX_HOLD` uses real `time.sleep` to create the 4s/5s shutdown and render races ([`tests/integration.rs`](../../tests/integration.rs#L3426-L3593), [`tests/integration.rs`](../../tests/integration.rs#L3596-L3661), [`tests/integration.rs`](../../tests/integration.rs#L3903-L3979)). The Claude no-registry fixture deliberately keeps the child alive while omitting its registry entry ([`tests/integration.rs`](../../tests/integration.rs#L3931-L3937)).

These boundaries explain why a paused Tokio clock is not a solution: there is no Tokio runtime in the application dependencies, and a Rust-side virtual clock cannot advance a Python process, `/proc`, a real file lock, a subprocess wait, or a filesystem observation. A future injected clock can make a pure Rust state machine deterministic, but the retained process tests still need wall time.

## Feasible fast-feedback shape

The safe shape is two explicitly named coverage lanes:

1. **Fast lane:** pure render-outcome/retry transitions, stall hash/debounce transitions, profile screen analyzers, and a small number of focused PTY smoke tests. It may use synthetic timestamps or a test clock only inside state machines that receive that dependency. It must retain assertions for the four-attempt park sequence, the one-sample transient rule, the second-stall re-arm, and zero-execution/failure visibility where applicable.
2. **Full lane:** the current all-target inventory and complete test set, including the real Claude 30s proof timeout, 3s shutdown grace, 4s/5s subprocess holds, process death, `/proc`/`flock` ownership, and provider-specific PTY gates. All tests remain visible with retries zero and no blanket filtering. This lane is the evidence for production-boundary coverage and cannot be promised under one minute from this study.

The split must report test inventory and evidence separately. Moving a test into the fast lane does not permit deleting its full-lane counterpart. A nextest process-per-test model can reduce environment contention, but it does not alter child-process wall time and does not by itself prove a sub-minute suite.

## Ranked implementation recommendations

1. **Instrument before changing waits.** Add test-only phase timestamps or a structured fixture trace for the two routed park tests: enqueue, worker completion, each render attempt start/end, retry wake, park, and final idle/send. Include poll counts and observed screen samples. Acceptance is a per-phase artifact for one pinned run, with the four misses and three retries still visible. This is the only way to separate the 32.2s intentional floor from queue/setup and scheduler slack.

2. **Extract the PTY render decision from the adapter I/O.** Keep `capture_visible`, paste, Enter, and the real 4s deadline in the E2E test, but move the occurrence-count/input-empty decision and timeout result into a small state machine that accepts samples and timestamps. Unit tests should cover rendered-and-submitted, rendered-but-staged, never-rendered, and deadline boundaries. The production default remains 300ms/150ms/4s; no test override is accepted until the unit contract and one real smoke test are in place.

3. **Extract stall debounce and episode transitions.** A pure state machine should accept screen hashes and timestamps and assert: first sample establishes a baseline; one transient candidate neither resets nor resumes; a confirmed change resumes; a later silence fires a second episode; spinner normalization does not count as motion. Keep one E2E test at the real 2s ticker and one configured silence budget. The existing `stall_sample` override is test-only and must not be expanded into a production default change.

4. **Use event/readiness synchronization in fixtures where the event is the contract.** Replace arbitrary mock startup sleeps with a readiness marker or an observed daemon event only when that marker is causally ordered after the child has painted and written its ownership evidence. Do not replace the 4s/5s holds, process death, registry absence, or ownership scan in the retained tests. An event-driven helper must fail closed when the marker is absent rather than treating a missing marker as ready.

5. **Consider a narrowly scoped test budget seam only after telemetry.** If the routed park tests still spend measurable scheduler slack, a test-only `ServeOptions`/fixture budget may shorten render and retry waits for the fast lane while asserting the production defaults remain unchanged. It must be explicit at the call site, unavailable to normal daemon startup, and paired with assertions for attempts, retry flags, park event, pane survival, and subsequent delivery. Do not use an environment-wide timeout, alter the production `RENDER_DEADLINE`, remove the 5s wake bound, or turn a task message into a notification just to make the test faster.

6. **Keep real deadline and ownership regressions in the full lane.** `pty_claude_resume_timeout_keeps_session`, `pty_shutdown_straggler_detaches_pane`, `pty_hot_restart_submitting_never_records_running`, and process-death/fence tests are testing operating-system and provider boundaries. Their pure decisions can be unit-tested, but at least one real fixture for each boundary must remain.

7. **Design the lane split and benchmark separately.** After code changes are reviewed, an Ops-admitted measurement should record cold and warm trees, exact SHA/toolchain/nextest, all-target name parity, pass/fail/skip/no-execution counts, per-test timings, and total runner-minutes across every job. No result from the current single run or the historical 272-test measurement should be presented as a current sub-minute guarantee.

## Risks and validation

Clock injection can make a state transition deterministic while hiding a race between the daemon thread, a capture thread, and a child process. A test budget override can pass while the production deadline is broken if the production-default path is not retained. A readiness marker can be stale or written before the ownership proof if its ordering is not explicit. Event-driven waits can also mask a missing notification unless their timeout and failure output remain visible.

Validation should proceed in this order: pure state-machine tests; the focused routed-park, transient-stall, Claude timeout, shutdown-straggler, and hot-restart tests; then an Ops-admitted benchmark on one pinned head. No new full-suite benchmark is justified by this source investigation alone. The production defaults and all process-boundary checks must be asserted in the review before any runner activation or workflow change.

This note therefore supports a narrowly scoped timer/state-machine follow-up and a separately reviewed fast/full lane design. It does not claim that the current complete suite is sub-minute or authorize shortening a production deadline.
