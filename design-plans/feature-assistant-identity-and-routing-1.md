### What to reuse from OpenClaw

The primary documentation read on 2026-10-25 distinguishes installation/provider onboarding from first-conversation BOOTSTRAP. Bootstrap asks what to call the agent, agrees a vibe, persists model identity and the identity displayed by UI/channels, and supports later `openclaw agents set-identity` updates. Cadence should reuse the conversational identity and consistent-display principle, not copy OpenClaw's configuration/credential format or its file-existence completion heuristic.

Cadence deliberately retains request-first optional questions, durable pending/complete/skipped/deferred lifecycle, current-turn authorization, and managed platform instructions. Avatar generation, creature/theme questionnaires, plugin recommendations, installation and provider setup are excluded.

## 1. Requirements & Constraints

- **REQ-001**: Assistant display name, user preferred address and workspace name are distinct concepts. Stable assistant id, alias, ownership and conversation ids are not display names.
- **REQ-002**: Phase 1 personal onboarding is normal chat: fulfill the user's actual request first, then optionally ask at most one question per turn. Example questions are “What would you like to call me?” and, on a later turn, “How would you like me to communicate?” A neutral concise, practical, friendly and uncertainty-explicit default applies until the user agrees a different style. Accept skip/later; resume only explicitly after defer.
- **REQ-003**: Personal `profile.name` continues to mean assistant display name; `profile.tone` means agreed communication/personality; `profile.preferences` contains agreed user preferences. Add optional `profile.user_name` only for an explicitly agreed preferred user address, stored in USER.md rather than IDENTITY.md. Do not infer identity from a chat mention or workspace/user display-name coincidence.
- **REQ-004**: A later explicit request such as “Call yourself Nova” or “Be more concise and formal” updates only the named fields through the existing revision-bound ACK. `update` preserves pending/complete/skipped/deferred state, other fields, history, stable identity and runtime ownership. Clearing the assistant name explicitly returns display to the localized unset fallback; it does not delete the assistant or reopen bootstrap.
- **REQ-005**: A single committed profile source drives model context and the authorized UI projection. Custom names remain literal across English/Traditional Chinese. Assistant/助理 is only the unset name fallback. UI must not optimistically claim a rename succeeded; refresh identity after accepted turn completion, and discard stale identity on session/workspace/assistant changes. An unreadable/refused identity is not silently treated as unset.
- **REQ-006**: Phase 1 also fixes identity display for the currently visible workspace coordinator. Its display name is workspace-owned and editable by a proven operator through the existing protected file writer. Default role description is Workspace assistant/工作區助理; internal alias remains `master`. Its communication/personality remains in the operator-owned SOUL.md. Never copy an owner's private profile into coordinator memory.
- **REQ-007**: Phase 2 makes Home and app-shell chat target the signed-in user's workspace-bound personal assistant, including owners/operators. One logical assistant/name/personality does not mean one shared transcript or provider session. Home and each installation/context/subject retain distinct authorized conversations and execution context.
- **REQ-008**: Master remains the workspace-owned coordinator for canonical approved jobs, reports, blockers and escalations. The owner's assistant is an ordinary personal-assistant instance, not a separate type and not the company coordinator. Ownership transfer does not transfer personal memory or orphan shared coordination.
- **REQ-009**: A personal assistant can ask Master a bounded read-only query. Original requester authority, resource scope and originating conversation survive the hop. Return an answer with supporting authorized references or an explicit refusal/unavailable result, not the shared Master transcript. Queries cannot dispatch, approve, publish or modify data, including when requested by an owner.
- **REQ-010**: Local and hosted use the same product ownership semantics, but retain distinct supported identity proofs. Local personal-assistant admission must exist before local recipient cutover. A locally executing worker connected to hosted coordination does not create a second logical assistant. Provider/runtime setup remains the host/operator's responsibility.
- **REQ-011**: Reuse `ui/src/features/agents/AgentAvatar.tsx`, its eleven existing AVATAR_LOOKS, `agentLook` precedence and existing pinned `params.look`; no new/generated avatar artwork or mandatory avatar ceremony. For a new personal assistant, derive the initial look from its immutable alias, not display name, then pin that look so future palette additions do not change it. Preserve existing pins; Master defaults to the existing robot when unpinned. An optional picker in assistant details may explicitly update the owning assistant's look through its guarded identity path; coordinator appearance remains operator-owned. Rename, locale, navigation, restart and credential rotation never reroll the look. Appearance never changes role, permissions or personality. Acceptance includes consistent header/sender/details avatars, owner isolation, later selection and rename stability on desktop/mobile. The static review uses in-memory pins and exported canonical artwork, not production persistence or authorization.
- **SEC-001**: Membership, principal/assistant ownership, original credential/CID, current turn/generation, resource access, revision fences and operation consent are mechanically checked. Persona text grants no tools, access or approvals; model instructions alone do not enforce query scope.
- **SEC-002**: Personal writes use the owning current-turn path; coordinator writes use proven operator authority. Unknown/foreign selectors, revoked membership and stale updates refuse before effects. Coordinator self-edit stays refused. HTTP peers must be at least as strict as the native guard.
- **SEC-003**: Master queries use isolated per-query model/tool context, with retrieval and tools restricted to the requester's permitted resources. Do not reuse an unrestricted company session and filter only its final prose. Send minimal relevant question/reference data; no personal profile, entire private history or another app's history.
- **SEC-004**: The daemon binds query ownership and reply destination from the verified originating turn; the model/browser cannot choose a user/org/reply conversation. Revalidate queued execution and reply delivery; removal/revocation cannot leak a late answer. Do not use generic unrestricted agent messaging as the new query interface.
- **CON-001**: Phase 1 preserves current Home/app-shell routing, coordinator privilege boundaries and existing setup policies. Personal bootstrap remains available on the current hosted private surface; a local user's per-person onboarding is part of phase 2, not an implicit phase-1 authorization bypass.
- **CON-002**: Existing Master/app transcripts retain workspace ownership, participant provenance and policy. Do not import them into a user's private history or relabel their authors during phase 2. No fallback to shared Master chat when personal authority is unavailable.
- **CON-003**: One feature ticket/PR per independently useful phase in this repository, no task-per-step tickets or unmerged stacks. Use the computed delivery evaluator, independently authored guard refusal, required reviews/operator approval, exact-head CI and actual Browser QA. Cross-repository changes require one linked companion outcome only when current schema evidence proves they are necessary.
- **CON-004**: No production state, installed binary, daemon, customer runtime, port 3010 or tailnet changes. Use owned isolated state and ports 3110-3199. Provider/login/issuer setup is not authorized by this plan; unavailable acceptance prerequisites are explicit blockers.
- **PAT-001**: Reuse bootstrap_files fd-relative bounded/no-follow managed-section reading/writing, member_profile_context, assistant_bootstrap_apply, existing verified session relay, operator file writer/digests, shared Conversation/Composer and canonical dispatch/review machinery. No duplicate membership directory, persona framework or new coordinator.

## 3. Alternatives

- **ALT-001**: Translate Assistant/助理 into another fixed brand name. Rejected: it remains a role label, ignores the saved identity, and does not support per-assistant later updates.
- **ALT-002**: Copy OpenClaw's full avatar/plugin/provider ceremony. Rejected: the useful requirement is identity/personality and persistence; provider setup is a separate host responsibility and earlier user-approved native UX excluded mandatory wizards.

- **ALT-004**: Rename Master as the owner's personal assistant or copy personal settings into Master. Rejected: company coordination, shared history and ownership transfer are not personal memory; current capabilities differ materially.
- **ALT-005**: Replace the recipient alias in the UI and grant personal assistants broad send/read/Master tools. Rejected: breaks existing app effects/attachments and creates a confused-deputy path.
- **ALT-006**: Allow read-only questions in Master's normal unrestricted session and filter prose afterward. Rejected: shared model context can contain data the requester cannot read. Scope retrieval and execution before a response is generated.
- **ALT-007**: Combine both phases into one large cutover. Rejected: naming/personality with later rename is independently useful and can be verified before changing identity/capability routing.

## 7. Risks & Assumptions

- **RISK-001**: The same Assistant/助理 label currently hides personal versus shared actors. Phase 1 must use the actual actor's profile and retain an explicit scope descriptor; otherwise it worsens the identity confusion.
- **RISK-002**: Existing name values may have been entered under ambiguous wording. Preserve them as stored; do not guess whether an existing value is the user's name or silently rewrite it. Clear current prompt semantics and let the authorized user correct it explicitly.
- **RISK-003**: Existing profile writes are atomic per managed file with a database revision fence, not proof of an atomic multi-file filesystem/database transaction. Acceptance must exercise failure handling; expose persisted truth after failures and do not claim all-or-nothing behavior without proving it. Do not expand into a generic transaction framework.
- **RISK-004**: A shared coordinator query can become a confused deputy or leak through provider memory even with a filtered final response. Scope retrieval, tools, session and return delivery mechanically before using it for personal assistants.
- **RISK-005**: A superficial actor swap breaks operator-only app capabilities, retained attachments, approvals, queue state or context isolation. Phase 2 acceptance includes those existing consumer-visible outcomes; no silent scope reduction.
- **RISK-006**: Changes to protected Master files may load only on a later provider session; current session refresh behavior must be measured in an owned fixture and accurately displayed. Do not restart a production daemon to obtain evidence.
- **ASSUMPTION-001**: The user requested a phased feature, not a deployment or broad host setup wizard. Default-neutral personality and existing generic unset name are acceptable until explicit personalization; no generated self-chosen name, avatar or plugin setup is required.
- **ASSUMPTION-002**: Logical personal ownership remains workspace-bound, including for owners. Cross-company personal-memory sharing and access by managers are not granted by this design.
- **ASSUMPTION-003**: A phase-2 local-principal proof can be implemented using supported native authority. It remains an explicit prerequisite to validate, not a claim that hosted personal-assistant authorization already works on local/tailnet boards.
